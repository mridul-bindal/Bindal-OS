In MongoDB, a database contains collections, and collections contain documents. A document is the basic unit of data. It resembles a JSON object, so it is easy for developers using JavaScript, Python, Java, or similar languages to understand. Documents may include scalar values, arrays, nested documents, and references to information stored elsewhere. MongoDB does not force every document in a collection to have the same set of fields, though applications often benefit from a consistent shape.

A collection is created automatically when its first document is inserted, unless an application explicitly creates it beforehand. Collection names should be clear and stable, such as users, orders, or inventoryItems. MongoDB permits documents in one collection to differ, but using a collection for unrelated concepts can make validation, indexing, and querying difficult. Separate collections are generally better when records have different lifecycles or access patterns.

Documents are identified by the _id field. If no _id is supplied, MongoDB creates an ObjectId, which includes a timestamp component and is designed to be unique. An _id cannot be changed after insertion. Other fields can be updated, added, or removed as application requirements change. Nested fields can be queried using dot notation, allowing specific data to be selected without flattening every structure.

Choosing what to embed and what to reference is a core modeling decision. Embed data that is normally read and updated together, such as order line items. Reference separate records when data is large, independently managed, or shared broadly. A good collection and document design reflects real application operations rather than copying a relational model mechanically.
