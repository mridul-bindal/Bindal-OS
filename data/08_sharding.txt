Sharding is MongoDB's method for distributing a large collection across multiple machines. It is used when a single server cannot provide enough storage capacity or throughput. A sharded cluster contains shards that hold data, configuration servers that store cluster metadata, and mongos routers that direct application requests to the appropriate shards.

Each sharded collection uses a shard key. MongoDB partitions the collection into ranges or hashed values derived from that key, then places chunks of data across shards. A good shard key distributes writes and storage evenly while supporting the application's most important queries. A poor choice can create hotspots, send most traffic to one shard, or force queries to inspect many shards.

Hashed shard keys spread values broadly and can help distribute inserts, but they are less useful for range queries on the original value. Ranged shard keys can support targeted range queries, yet monotonically increasing fields such as timestamps may concentrate new writes on one location unless the design is adjusted. Compound shard keys can sometimes balance distribution and query targeting more effectively.

Sharding adds operational and modeling complexity, so it is not the first solution for every performance issue. Teams should first use effective indexes, efficient queries, and a suitably sized replica set. Before sharding, they should forecast data growth, test candidate keys with real workload patterns, and understand which queries include the shard key. Continuous monitoring is essential because traffic patterns can change after deployment.
