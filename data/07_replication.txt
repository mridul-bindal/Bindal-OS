MongoDB replication improves availability by maintaining copies of data on multiple servers. The standard replication unit is a replica set. One member acts as the primary and receives normal write operations. Other members, called secondaries, copy the primary's operation log and apply the same changes. If the primary becomes unavailable, eligible members can elect a new primary automatically.

Applications typically connect using a replica-set connection string rather than naming only one server. The MongoDB driver discovers the current topology and can route operations correctly after an election. Reads normally go to the primary for the strongest default consistency, but read preference can allow selected reads from secondaries when slightly stale data is acceptable. This tradeoff must be chosen deliberately, especially for user-facing workflows.

Write concern determines how much acknowledgement a write requires. For example, a majority write concern asks for confirmation from a majority of voting replica-set members. Read concern controls the consistency guarantees for reads. Together, these settings let teams balance latency, durability, and consistency according to the importance of each operation.

A production replica set should span failure domains such as availability zones or data centers while keeping network latency reasonable. It needs an odd number of voting members for reliable elections, plus monitoring for replication lag, disk capacity, and member health. Backups remain necessary: replication protects against server failure but can also replicate an accidental deletion or faulty update.
